# 공통 글쓰기 원칙

고객 메시지, 제품 문서, 내부 문서, 스킬과 프롬프트에 공통으로 적용합니다. 글의 독자와
목적에 맞는 추가 규칙은 각 글쓰기 프로필에 둡니다.

## 쓰기 전에 세 가지를 정하기

1. 누가 이 글을 읽는지 정합니다.
2. 읽은 사람이 무엇을 알거나 할 수 있어야 하는지 한 문장으로 적습니다.
3. 같은 개념에 사용할 용어를 먼저 고릅니다.

독자나 결과가 두 개라면 문서를 나눕니다. 한 문서에 여러 목적을 넣으면 제목과 탐색 구조가
내용을 설명하지 못합니다.

## 한 문장에 한 가지를 말하기

문장을 짧게 만드는 것보다 한 문장에 하나의 판단이나 행동을 담는 것이 중요합니다. 짧은
문장을 연속으로 끊어 메모처럼 만들지 않습니다.

| 고칠 것 | 고친 것 |
|---|---|
| `버튼을 누르면 저장되며 목록으로 이동하고 결과를 확인할 수 있습니다.` | `저장을 선택하세요. 목록으로 돌아오면 저장한 항목을 확인할 수 있습니다.` |
| `설정 확인. 링크 생성. 고객에게 전송.` | `설정을 확인한 후에 링크를 만드세요. 링크를 받을 고객을 확인하고 전송하세요.` |

## 사람과 행동을 주어로 두기

명사형과 수동태보다 구체적인 동사를 사용합니다. `수행하다`, `진행하다`, `처리되다`를
지워도 뜻이 같다면 더 직접적인 동사로 바꿉니다.

| 고칠 것 | 고친 것 |
|---|---|
| `설정 변경 작업을 수행합니다.` | `설정을 변경합니다.` |
| `변경 사항이 적용되어야 합니다.` | `관리자가 변경 사항을 적용해야 합니다.` |

## 조건을 행동보다 먼저 쓰기

조건이 있는 절차에서는 독자가 행동을 시작하기 전에 조건을 알려 줍니다.

| 고칠 것 | 고친 것 |
|---|---|
| `저장을 선택하세요. 공개 폼인 경우에만 사용할 수 있습니다.` | `공개 폼이라면 저장을 선택하세요.` |
| `링크를 다시 만드세요. 기존 링크가 만료되었을 때 필요합니다.` | `기존 링크가 만료되었다면 새 링크를 만드세요.` |

## 같은 뜻에는 같은 말을 쓰기

한 문서에서 같은 동작을 `추가`, `등록`, `생성`으로 바꾸어 쓰지 않습니다. UI에 표시되는
이름은 화면과 똑같이 씁니다. 줄임말은 처음 나올 때 풀어 씁니다.

번역할 때에도 제품 개념의 대응 관계를 유지합니다. 문장을 직역하지 말고 같은 사실과 결과를
각 언어에서 자연스럽게 설명합니다.

## 의미 없는 도입과 평가를 지우기

`아시다시피`, `결론적으로`, `여기서 중요한 점은`처럼 내용을 더하지 않는 도입을 지웁니다.
`쉽게`, `간단히`, `당연히`처럼 독자의 경험을 대신 판단하는 말도 쓰지 않습니다.

## 문장부호를 기능에 맞게 쓰기

문장을 잇기 위해 엠대시, 화살표, 별표 기호를 사용하지 않습니다. 쉼표를 쓰거나 문장을
나눕니다. 단, 코드, 파일 경로, 명령어, 데이터 형식과 인용한 오류 메시지는 원문을 보존합니다.

## 사실과 예시를 구분하기

제품 동작은 코드, 실제 화면, 테스트 또는 공식 자료에서 확인합니다. 예시는 예시라고 밝히고
실제 데이터처럼 쓰지 않습니다. 확인하지 못한 내용을 자연스러운 문장으로 채우지 않습니다.

## 보내기 전에 확인하기

- [ ] 독자와 한 가지 결과가 분명합니다.
- [ ] 한 문장에 하나의 판단이나 행동만 있습니다.
- [ ] 조건이 행동보다 먼저 나옵니다.
- [ ] 같은 개념에 같은 용어를 썼습니다.
- [ ] 코드와 식별자, 명령어, 오류 메시지를 바꾸지 않았습니다.
- [ ] 근거 없이 제품 동작을 단정하지 않았습니다.
- [ ] 의미 없는 도입과 난이도 평가를 지웠습니다.
